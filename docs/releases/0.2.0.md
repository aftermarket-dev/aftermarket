Aftermarket 0.2.0 adds its second tool: **AfterAPI** (`aftermarket adapt`). It keeps an old client working after its API was replaced, with one mapping per old endpoint.

- **Endpoint mapping.** Path and query parameters move into the new URL, the method can change, and query parameters the mapping doesn't use are passed on as the client wrote them.
- **Templates.** The new request body is built from the old one, and the old response shape is rebuilt from the new one: `$.customer.id`-style paths, `$params.name` for URL parameters, and `$each` with `$item` to turn one list into another. Fields the template doesn't name are left out.
- **Status and error mapping.** For example, `201` becomes `200`, `204` becomes `200` with a body, and `{"error": {"message": ...}}` becomes `{"message": ...}`.
- **Header renames.** Credentials are never touched.
- **All or nothing.** A request or response that can't be translated safely passes through exactly as it was sent and is logged as skipped.
- **The same tools as AfterPatch:** dry run, the audit log (with path patterns instead of values), `adapt check` and `adapt test` with the shared fixture format.

The new `examples/customer-api` has a v1 service, a v2 service and the old client's test suite of twelve checks. It passes against v1, fails every check against v2 directly, and passes every check against v2 through adapt.

Two fixes in AfterPatch, found by the review before this release:

- A dry run no longer turns a slow response body into a `504`. It now waits as long as the upstream takes, so it really changes nothing.
- A client that stalls while sending a body a rule needs now gets `408` after `upstream_timeout`, where before it could hold a connection open indefinitely.

`set` values that are numbers too large for JSON readers, such as `1e400`, are now rejected when the rule file loads.

Recorded results are in `test/results`. The full mapping format is in `docs/adapt.md`.

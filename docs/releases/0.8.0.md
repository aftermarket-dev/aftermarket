Aftermarket 0.8.0 adds **AfterSchema** (`aftermarket schema`). When an app's SQLite database moves to a new schema, the old reports, scripts and integrations that still ask for the old tables can keep working: you describe the old tables in terms of the new ones, and AfterSchema writes views that show the old tables again.

- **`schema diff`** lists every change between two schemas (tables, columns, types, NOT NULL, defaults, keys, indexes, foreign keys, views and triggers) and marks the ones that break old readers. With a mapping, the changes its views take care of are marked covered. It exits 1 on anything breaking left uncovered, so it fits in CI.
- **`schema compat`** writes the views to one `.sql` file to review and apply yourself. The same mapping always gives the same bytes, and nothing is written unless every view compiles on the new schema.
- **`schema check`** compiles each old query on the new schema, with or without the views, without running it, and lists every one that fails with its line.
- **`schema test`** runs every old read on the old database and on the new one through the views, and compares the rows exactly: values, types and column names.
- **No database is ever written.** Databases are opened read-only through the `sqlite3` program in its safe mode, `.sql` files are loaded into memory, and every piece of SQL from a file or a mapping is checked so the `sqlite3` shell can never take any of it as one of its own commands.

The new `examples/legacy-shop` has a shop's database at 1.0 and 2.0 and a dozen old report queries. Only 1 of the 12 compiles on 2.0 alone; with the views all 12 compile and give the same rows as on 1.0.

AfterSchema needs the `sqlite3` command, 3.37 or later. Views serve reads; writes through them, an apply step and other databases are not part of this release.

Recorded results are in `test/results`. The full format is in `docs/schema.md`.
